# 진행상황

## 2026-10-19: DDD 패키지 구조 정리

- `product`, `reservation`을 기능별로 두고 각각 `domain`, `application`, `infrastructure`, `api`로 나눴다.
- `domain`은 재고·예약 상태 규칙과 저장소 인터페이스를 가진다. `application`은 유스케이스와 트랜잭션을 담당한다. `infrastructure`는 Spring Data JPA 구현과 초기 데이터·스케줄러를, `api`는 HTTP 요청·응답 변환을 담당한다.
- 의존 방향은 `api → application → domain ← infrastructure`로 정리했다. 도메인은 HTTP 상태코드에 의존하지 않고, 애플리케이션은 요청·응답 DTO를 사용하지 않는다.
- 기존 JPA 엔티티를 별도의 영속성 모델로 복제하지 않고 도메인에 유지했다. 이번 단계의 목적은 패키지 경계와 의존 방향을 분명히 하는 것이며, JPA 어노테이션까지 분리하는 작업은 범위에 넣지 않았다.
- Java 패키지와 애플리케이션 이름의 `invertory` 오타를 `inventory`로 수정했다. API 경로와 응답 필드는 유지했다.

## 2026-10-07: 기본 API 구현

- 초기 상품 `limited-keyboard`(10개), `limited-monitor`(3개)를 H2 인메모리 DB에 준비한다. 이미 있는 상품의 재고는 초기화 과정에서 덮어쓰지 않는다.
- 재고 조회와 예약 생성·조회·확정·취소 API를 구현했다.
- 같은 상품의 같은 `requestId`와 동일한 요청 내용은 기존 예약을 반환한다. 요청 내용이 다르면 `409 DUPLICATE_REQUEST_MISMATCH`를 반환한다.
- 예약 수량은 `availableStock → reservedStock → soldStock`으로 이동한다. 취소·만료 시에는 `reservedStock → availableStock`으로 되돌린다. 각 변경은 예약 상태 변경과 같은 트랜잭션에서 처리한다.
- 확정·취소는 `RESERVED`에서만 새로운 상태로 전이한다. 이미 같은 상태로 끝난 요청은 결과를 그대로 반환한다.
- 생성 시각과 만료 시각은 UTC `Instant`로 기록한다. 주입한 `Clock`을 기준으로 120초 만료를 판단하며, 1초 간격의 작업과 API 요청 시 만료를 반영한다.
- 만료 반영을 별도 트랜잭션으로 처리한다. 만료 후 확정·취소 요청이 `409 INVALID_RESERVATION_STATE`를 반환해도 만료 상태와 재고 복구가 롤백되지 않도록 하기 위해서다.

## 확인한 내용

- 기존 `contextLoads()`를 포함한 `./gradlew test --no-daemon`이 통과했다. 새 테스트 코드는 작성하지 않았다.
- 실행 중인 앱에 HTTP 요청을 보내 최초 예약 `201`, 동일 요청 재전송 `200`, 다른 내용의 `requestId` 재사용 `409`, 재고 부족 `409`, 잘못된 입력 `400`, 확정·취소 반복 `200`, 잘못된 상태 전이 `409`를 수동 확인했다.
- 수동 확인에서 수량 2 예약 후 재고는 `(available, reserved, sold) = (8, 2, 0)`, 확정 후 `(8, 0, 2)`였다.
- 만료 시각이 지난 예약을 조회하니 `EXPIRED`였고 `limited-monitor` 재고는 `(3, 0, 0)`으로 복구되어 있었다. 이후 확정·취소 요청은 모두 `409 INVALID_RESERVATION_STATE`였다.

## 남은 범위

- 요청에 따라 동시성 제어와 동시 요청 검증은 이번 구현에서 제외했다. 여러 요청이 같은 재고나 예약을 동시에 변경하면 과제 문서의 정합성 조건을 아직 보장하지 않는다.
- 새 테스트 코드를 작성하지 않았으므로 정상·경계·만료 시나리오의 자동 회귀 검증은 남아 있다.
- 과제 문서는 Java 25+를 요구하지만 현재 설치된 JDK는 23까지라 빌드 설정의 Java 21을 유지했다.
